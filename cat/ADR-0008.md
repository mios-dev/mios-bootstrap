# ADR-0008 — MiOS-Cat: the unified, SSOT-driven USB installer/flasher

**Status:** Accepted · **Scope:** `cat/` (MiOS-Cat.bat + resources) · **Relates to:** ADR-0003 (SBOM-not-hardcode), ADR-0009 (operator-defined SSOT), ADR-0010 (SSOT-as-dotfiles)

> Breadcrumb ADR. The authoritative config is `[cat]` (+ `[cat.*]`) in the SSOT
> (`usr/share/mios/mios.toml`, seeded to the repo-root `mios.toml`). This file records
> the *why* so the launcher's structure is not mistaken for incidental.

## Context

MiOS-Cat is the one USB that carries **all** MiOS deploy formats on Ventoy (GPT/UEFI +
Secure Boot shim), modeled on MediCat. It must build a **real, bootable, safe** USB and
must stay fully SSOT-driven — no hand-maintained or hardcoded config, nothing skipped.

## Decisions

1. **One `[cat]` SSOT block.** The launcher's settings (drive, label, MediCat version,
   cache path, Ventoy version, builder/log overrides) come from `[cat]` in `mios.toml`.
   The former `[medicat]` block is **consolidated into `[cat]`** (T-258b). The `.bat`
   loads it in a single PowerShell pass (section-agnostic key read spanning `[cat]` +
   `[colors]`); hardcoded values remain only as degrade-open fallbacks for a missing SSOT.

2. **No hand-pinned dependency versions (ADR-0003).** `ventoy_version = "latest"` is an
   **intent sentinel**, not a pin. MiOS targets the newest upstream **globally**: the
   flasher resolves the latest Ventoy release live from the GitHub API at runtime, and the
   build records the resolved version to the SBOM. There is **no stale offline fallback
   pin** — if nothing resolves (offline, no build-recorded pin, no staged Ventoy) the
   flash **fails loud** rather than shipping a blind bootloader.

3. **Partition layout — degrade-open.** Ventoy data partition (label `MiOS-Cat`) + a
   `MiOS-Repo` shadow-config/offline-payload partition (always present). On disks **≥512 GB**
   a persistent `MiOS-Data` vault partition is also created; smaller disks skip it and give
   the remainder to `MiOS-Repo` — **never abort** on a small disk.
   *(Follow-up: source the 512 GB threshold from `[cat.data_partition].min_disk_gb` once the
   loader gains numeric-key support; presently a documented default in the `.bat`.)*

4. **`repos/` staging layout, tolerant consumers.** Repos stage to
   `MiOS-Repo\repos\{mios-bootstrap,MiOS}` (T-260a). Both offline consumers — the Linux
   kickstart (`mios-kickstart.cfg`) and the Windows `bootstrap_root` resolver — scan **the
   partition root AND `repos/`**, so no single path can strand an offline install (T-260c).

5. **Shadow-config "brain."** The live SSOT (`mios.toml`), the architecture diagram
   (`mios.html`), and a self-copy of the launcher are staged at the `MiOS-Repo` root
   (T-260b) so a booted/target system can re-read config, re-open the topology, or re-run
   the flasher fully offline.

6. **Secure Boot + UEFI + GPT by default.** `secure_boot=Enabled` (Ventoy `/S` shim),
   `partition_scheme=GPT`. Not optional defaults — the shipped posture.

## Deploy targets the USB produces

- **MiOS-Xbox** — a **universal** Windows image: `bake_drivers=Disabled` by default →
  pure Windows inbox/base drivers for global all-platform support (baking the build host's
  own drivers would tie the image to one machine). Universal **VM** drivers (virtio +
  ivshmem/Looking-Glass) still ship, injected by `New-MiOSISO`.
- **MiOS Linux (MiOS-Dev bare-metal)** — a **mutable Fedora minimal server** provisioned
  via Butane/Ignition + the `build-mios.sh` overlay, at **parity with the MiOS-Dev WSL**
  deployment but bare-metal-unlocked. (Immutable `bootc install` remains a separate mode.)

## Consequences

Every USB is SSOT-derived, offline-capable, and safe (the auto-wipe rescue path FATAL-aborts
rather than falling through to wiping every disk). Version drift is impossible-by-construction
for Ventoy (resolved, not pinned). Drift-gate `verify` must stay green after these changes.
